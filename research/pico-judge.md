# Pico Judge — 1M Parameter Shell Command Classifier

A purpose-built binary classifier that replaces the hardcoded `isSafeBashCommand` whitelist. Sits in the permission gate between the agent model and `exec(sh -c)`. Safe or not. That's it.

## Why

The current permission system is a static whitelist of binaries (`cat`, `ls`, `grep`, ...) with heuristic checks for redirects, subshells, and dangerous flags. It can't reason about intent or context. `rm -rf /tmp/test` and `rm -rf /` are the same pattern to a regex.

Meanwhile, the system prompt that tells large models how to be safe is ~10,000 words. The tokenized weight of *telling* a model to be careful is larger than a model that *is* careful.

## Architecture

- 1M parameters, binary classifier
- Input: tokenized shell command + working directory context
- Output: safe / unsafe (single logit)
- Quantized, fits in L2 cache
- Inference in microseconds on CPU, near-zero on ANE/GPU

## Training data — synthetic, generated by larger models

The expensive model (Opus) generates the training data. The tiny model distills the judgment.

Pipeline:
1. Opus generates diverse shell commands with context (cwd, intent, filesystem state)
2. Opus labels each: safe/unsafe + reasoning
3. Multi-model consensus filter — run each example through multiple large models, keep agreements
4. Train pico on labels only, discard reasoning
5. RL in containers for edge cases synthetic data missed

Examples of what the training data captures that a whitelist can't:
- `rm -rf /tmp/test` (safe — scoped temp dir) vs `rm -rf /` (unsafe)
- `perl -pi -e 's/foo/bar/' src/main.ts` (safe — scoped edit) vs `perl -pi -e 's/foo/bar/' /etc/passwd` (unsafe)
- `git push --force` (context-dependent — personal branch vs main)
- `curl -o ./tool https://...` (safe — local) vs `curl ... | sh` (unsafe — pipe to shell)
- `chmod 777 .` (probably a mistake but not catastrophic) vs `chmod -R 777 /` (catastrophic)

## Training cost

| | |
|---|---|
| Model size | 1M params (~4MB fp32) |
| Training data | ~1M labeled examples (generated by Opus in a day) |
| Hardware | Single consumer GPU (4070, 12GB VRAM) |
| Time | Minutes. Model + optimizer + batch fit in memory with room to spare |
| Real cost | The Opus API calls to generate training data. Training itself is a rounding error |

## Feedback loop

Every time a user overrides the gate — allows something it flagged, or denies something it passed — that's a training signal. The correction data accumulates locally, periodic fine-tuning closes the gap. The judge improves from use.

## Integration

Slots into the existing architecture with zero changes to the agent loop:

```
// current: static whitelist
if ((toolName === "Bash" || toolName === "exec") && input?.command && isSafeBashCommand(input.command)) return false;

// future: pico judge
if ((toolName === "Bash" || toolName === "exec") && input?.command && await picoJudge(input.command, cwd)) return false;
```

Latency budget: the agent model takes 2-7 seconds per response. The pico judge takes microseconds. Invisible in the pipeline.

## The stack

The complete giverny safety + execution stack:

- `exec(sh -c)` — one tool, the entire Unix environment
- `bridge-loop.ts` — generate, gate, execute, loop
- pico judge — 1M params, safe/unsafe, microseconds

No framework, no plugin system, no tool registry, no 10,000-word safety prompt. Three small things that compose.
